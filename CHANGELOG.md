The host supplies the store, catalog, clock and authorization (`Authorize` runs before every tool call, resource read and prompt and refuses with the code `mcp.not_authorized`). `brain-mcp --workspace <folder> [--catalog <file>] [--language en|es]` serves the same tools over standard input and output (`FileAuthoringStore`; the protocol is the only thing on standard output; one-line errors on standard error; exit codes 0, 1, 2 usage, 3 workspace, 4 catalog) and is packed as a .NET tool by `dotnet pack` of the solution. ## 0.3.0 (2026-11-23)

- W1-F: purge commands on `Synapbiz.Brain.Host.Postgres`. `IProcessEngine` gains `PurgeInstanceAsync(tenantId, instanceId, PurgeMode)` (removes a root instance and every descendant, at any depth, with their history, timers, waits, tasks, effects and inbox rows in one transaction, all or nothing; `FinishedOnly` refuses a root that is still going, `Force` erases it whatever its state; unknown id is `NotFound`, a child is refused as `process.purge.not_root`; the result carries the exact number of rows deleted per table), `PurgeFinishedBeforeAsync(tenantId, before, limit)` (up to 500 finished trees whose root was last written before an instant, oldest first, one transaction per tree, `skip locked`, `More` reported honestly) and `PurgeEventsBeforeAsync(tenantId, before, limit)` (up to 5000 event ids, after which a purged id is a new event). The records `PurgeResult`, `PurgeCounts`, `PurgeBatchResult` and `PurgeEventsResult` and the enums `PurgeMode` and `PurgeStatus` are public. Lock discipline: a purge never waits for a row lock while it holds one. An attempt reads the ids of the tree without locking, locks all of them in one `for update skip locked` statement (fewer rows than ids means another transaction holds part of the tree: it rolls back and gives everything up), walks the tree again under the locks and decides (exists, root, finished) only there; `PurgeInstanceAsync` retries after a short randomized pause until the new option `ProcessHostOptions.PurgeLockTimeout` (default 10 seconds, greater than zero and at most 5 minutes) passes and then returns `Refused` with the new code `process.purge.busy`, nothing changed; `PurgeFinishedBeforeAsync` makes one attempt per tree and skips one that is not wholly acquired. Because a purge transaction never waits while it holds a lock it cannot be part of a deadlock cycle, with a publish (which locks its targets in instance id order), the pump, a command or another purge; the tests run publishes that hold one target open and many rounds of publishes, pumps and purges and require no `40P01`. the pump drops, without error, an item whose instance was purged after it read it, and the result of a port call that comes back after its case was purged is dropped with the new log line `process.effect.orphaned` (a purge logs `process.instance.purged`, ids and counts only). Migration `0004_purge.sql` adds three indexes (finished roots by update time, event ids by receipt time, inbox rows by instance), additive; like `0003` it creates them inside the migrator's transaction, so writes to those tables wait while it runs. A statement that PostgreSQL refuses no longer surfaces as an `ObjectDisposedException` over the real error (the session no longer rolls back a transaction that Npgsql disposed after a critical failure, and a commit that failed surfaces as its own exception). Tests: trees with children and grandchildren and exact counts, tenant isolation, refusals, a tree 40 levels deep, a child committed between the walk and the locks, a tree held for longer than the timeout, two deadlock scenarios against a publish, atomicity with a failure injected into each table, every kind of work item read by a pump before a purge, an effect in flight, a purge against three pumps for 80 rounds and publishes, pumps and both purge commands for 60 rounds each with no deadlock and no half tree at any observation, the boundary, limit, order, locked-tree and `More` rules, event ids, logging hygiene and the guide example. Docs: the reference page (commands, "What remains after a purge"), the operations section of the consumer guide with a compiled example, `docs/architecture/overview.md`. `IProcessEngine` gained members in this release (W1-E: `ListInstancesAsync`, `CountInstancesAsync`, `GetCaseAsync`, `ListChildrenAsync`; W1-F: `PurgeInstanceAsync`, `PurgeFinishedBeforeAsync`, `PurgeEventsBeforeAsync`), so a consumer's own implementation or fake of the interface must add them. The version is now 0.3.0 for all seven packages; the other six packages are unchanged in content.
- W1-E: cockpit queries on `Synapbiz.Brain.Host.Postgres`. `IProcessEngine` gains `ListInstancesAsync` (filters by process, status, stage, roots only and needs attention; keyset paging by creation time and instance id), `CountInstancesAsync` (per process, status and stage), `GetCaseAsync` (an instance with its descendants to depth 16, their open tasks, next timer due and awaited event names, read in one repeatable-read transaction) and `ListChildrenAsync`, returning the new `ProcessInstanceSummary` (the instance without its state, with its open tasks and suspended descendants counted). The queries are read-only, filter by tenant first and never read or decrypt the state. Migration `0003_cockpit.sql` adds two indexes on `process_instance` and changes no table or column. `Synapbiz.Brain.Process` and the other packages are unchanged; the consumer guide section 8 replaces the walk through the history of the parent by `GetCaseAsync`.
